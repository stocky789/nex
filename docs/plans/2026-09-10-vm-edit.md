# Edit an existing VM

Date: 2026-09-10
Status: Implemented on main on 2026-09-10 with Go, contract, UI, simulated-browser and real-host
libvirt evidence; open: independent review. See [QA checks](../qa/vm-edit/checks.md).
Parent: [platform plan](2026-09-08-nex-platform.md) [Phase 2](2026-09-08-nex-platform.md#2-one-host-vm-management),
item 4 ("edit while stopped where required"), and the [VM creation system](2026-09-10-vm-creation-system.md)
whose follow-ups named this as the next slice.

## Scope and decisions

project owner's direction (2026-09-10): edit a VM **in place on its General tab**, where the details already
live, rather than in a separate form; and do not word this as "stopped-VM editing" — whatever a
running VM can take (adding a network interface, for example) must be editable while it runs, and
only the fields that genuinely need the guest stopped are gated on that.

- **One edit request carries the whole desired definition.** `PUT /api/v1/vms/{id}` takes the same
  shape as creation plus a stable `request_id`; the host receives a `vm-update` command carrying the
  full `VMCreateSpec` at the next `revision`. There is no per-field endpoint. This keeps replay,
  validation and adoption identical to creation and lets the UI submit one form.
- **Nex Core decides what applies live.** Core compares the requested definition with the one in
  its journal and classifies every difference:

  | Change | While running | Stopped |
  |---|---|---|
  | Description, guest OS hint, autostart | Yes | Yes |
  | Add a VirtIO or SCSI disk; add a network interface | Yes (hot-plug, persisted) | Yes |
  | Add a SATA disk | No — QEMU cannot hot-plug SATA | Yes |
  | Remove a disk or a network interface | Yes (hot-unplug, persisted; the guest must release it) | Yes |
  | Insert, swap or eject the install ISO | Yes (`change-media`, persisted) | Yes |
  | Name, vCPUs/topology/model, memory mode or size, firmware, machine type, any boot order | No — stop the VM first | Yes |
  | Existing disk's bus; existing interface's network, adapter model, MAC or MTU | No — stop the VM first | Yes |
  | Existing disk's storage target, size or provisioning | Never — refused on both sides | Never |

  A running VM whose request includes any "stop first" change is refused by Core before any
  effect, naming the field. The Controller mirrors the same rule in the form so the field is
  disabled with that reason while the VM runs, but Core's observed state is the authority.
- **Identity of devices across an edit.** Disks are matched by name (the name is the identity;
  renaming a disk is not offered). Interfaces are matched by MAC: the Controller freezes every
  derived MAC into the definition at the first edit, so removing interface 1 never changes
  interface 2's address. Disk target names (`vda`, `sda`…) are recorded in the journal at creation
  and kept on every edit; a new disk takes the next free letter.
- **Every VM has a CD drive.** Creation now always defines one SATA cdrom device, empty when no
  ISO was chosen, so an ISO can be inserted or ejected later without hot-plugging a SATA device.
  q35 definitions list the PCIe root complex and enough root ports for every PCIe device plus four
  spares, because libvirt consumes explicitly listed ports first and adds no spare beside them
  (observed on a real host: "No more available PCI slots" with four listed ports).
- **Removed disks are retained, never deleted.** An edit that drops a disk detaches it and records
  the retained file in the journal; deleting data is the separate deletion slice's job and needs
  its own confirmation. Retained files are listed in the task result.
- **Stopped path is a redefine.** With the VM shut off, Core allocates any new disks, renames the
  domain if needed (`domrename`), regenerates the complete domain XML from the new definition,
  `define`s it, sets autostart, and observes the persistent definition and per-disk ownership
  exactly as creation does. **Running path is device operations only**: `attach-device` /
  `detach-device --live --persistent`, `change-media --live --config`, `autostart`; then the
  persistent definition is observed against the regenerated XML. Definitions are compared by
  device identity (target / MAC), not position, because libvirt orders hot-plugged devices itself.
- **Durable state stays on the host.** Each successful `vm-update` is a journal entry on the pool
  master; `Inventory.managed.vms` reports the *current* definition (latest revision) with its
  `revision`, and the Controller refreshes its mirror from every report. A replaced Controller
  adopts the current definition and revision, so its first edit is accepted.
- **Concurrency.** One `vm-update` or `vm-power` request per VM may be queued or dispatched; a
  second is refused (409). Core refuses a revision other than current + 1, so a stale edit after
  Controller replacement fails cleanly instead of applying an old definition.
- **Out of scope, recorded:** disk resize; moving a
  disk to other storage; renaming a disk; re-placing a VM on another host (Phase 4/7); live memory
  or vCPU hot-add (possible with the balloon and vcpu hot-plug, not built). VM deletion with
  optional disk wipe is implemented separately (see the delete guide).

## API impact

**New contract**: `updateVM` (`PUT /api/v1/vms/{id}`), the `vm-update` command (payload
`VMCreateSpec` with `revision`), the `vm-update-v1` host capability and the `vm-update`
operation/audit kind. **Changed contract**: `VMCreateSpec` gains `revision` (0 at creation),
reported back in `Inventory.managed.vms`. Authentication, authorization, validation, errors,
asynchronous result, replay and outage behavior follow `createVM`/`powerVM`; an older Core
without `vm-update-v1` is refused with 409 at request time.

## Guide impact

**Updated**: new [Edit a virtual machine](../guide/edit-virtual-machine.md) page; status wording in
[Control VM power](../guide/vm-power.md) and the create page that said editing was unavailable.

## State

`state.owner: core` — the `vm-update` journal entry on the pool master; recovered by a fresh
Controller from `Inventory.managed.vms` (current definition with `revision`).

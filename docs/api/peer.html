Nex Core pool peer API — 0.1.0

Internal Core-to-Core pool peer contract; not a client or Controller API. Nex Controller never calls it and holds none of its state: membership, the pool CA, repository reservations, pool VM execution records and clustered-storage operations are durable on the pool master Core (peer probe leases and access observations are process-local). Served on the dedicated peer HTTPS listener (--pool-peer-listen, default :9444, on nex-core-local and nex-core-agent), TLS 1.3 only, with server limits of 5 s header, 15 s read, 30 s write and 16 KiB headers. The listener requests a client certificate and verifies it against the pool CA when presented; every route except join then admits only the peer named by its security requirement. Clients pin the pool CA and expected host ID (and, master to member, the membership certificate SHA-256), refuse redirects and time out after 15 s. Errors are short text/plain bodies. Development protocol: deploy matching Core versions in a pool; additive acknowledgements (probe mode echo, update_accepted, spec_match) let newer peers fail closed against older ones. Controller-hosted qnetd witness candidate and certificate-registration routes are implemented for Core; two-host SBD arming and witness-loss promotion proof remain withheld.

POST /api/v1/pool/join

Redeem a pool join offer

Served by the pool master; the only peer route without a client certificate. Authority is the single-use offer created by the master Core local API: it binds pool, master host, member host ID and CSR SHA-256, and expires after 15 minutes. The master signs the CSR with the pool CA, appends the member as ready, increments the membership generation and persists before replying. A retry of the same offer, host ID and CSR after a lost response returns the same certificate and current membership; a different key or an already-admitted host is refused. The member pins the pool CA and master host ID from the offer, verifies the returned certificate against its pending key, then persists and completes a Core-owned rehome. Body at most 1 MiB.

POST /api/v1/pool/advertise

Advertise member peer origin, system UUID, management-controller report and watchdog

Served by the pool master. Records the calling member's peer listener origin, its own SMBIOS system UUID, its own management-controller report and its own watchdog capability in the master membership: the origin so the master can later contact that member (PoolMasterCertificate routes), the UUID so another host can prove a management controller belongs to this machine before fencing it, and the watchdog so the master can answer whether that host could shut itself out after it is gone. Each field is recorded on its own and either may be omitted; both are observations and move no membership generation. The member is identified only by its certificate; input cannot name another member. Last write wins and repeats are idempotent; an unknown member is accepted without change. The member persists a pending origin first and retries it at startup until the master returns 204. Body at most 4 KiB; any non-POST method is rejected as 400 after authentication.

POST /api/v1/pool/placement

Check one member's native VM placement

Served by the current ready selected member at its advertised origin and called only by its current pool master over pinned mutual TLS. The request names one exact vm-create or vm-update command and the current membership generation. The member reads its current durable managed state, including the no-effect clustered-storage admission context, and performs no mutation, reservation, or start. It returns only after native placement checks complete and after rechecking membership. The master accepts an acknowledgement only when generation, operation_id, vm_id and vm echo exactly and accepted is true; before saving its definition or reservation it takes its durable locks and rechecks that same membership generation. A missing acknowledgement field from an older Core, timeout, connection failure, refusal or membership change fails placement closed. replay:true means the target recognized the identical existing journal command and did no fresh native check; it may confirm only an existing durable master placement record, never create one. A failed placement admission for an exact journalled definition command does not authorize native execution or journal reconciliation; Core reports needs_attention. Retry only the same operation and command after reconciliation; changed input with the same operation is refused. Requests and master-accepted replies are bounded to 128 KiB; the member's preflight deadline is 20 seconds.

POST /api/v1/pool/replica

Store one signed authority replica on this member

Master to member over pinned mutual TLS, bounded to 1 MiB with no trailing JSON. The member verifies that the replica names its own pool and its current master, is addressed to itself, declares every section with matching digests, and is signed by the pool CA it pinned at join; it then writes pool-replica.json atomically at mode 0600 and acknowledges. It never acts on the contents: no membership, VM, storage, network or media record on this host is read from or changed by a replica, a replica grants no execution, and no health judgement is derived from one. Idempotent: the same generation with the same content returns the same acknowledgement. A strictly lower generation is refused, and the same generation with different content is refused rather than overwriting. The wrapped pool CA key is stored sealed and is not opened by anything in this release. Pushes are driven by the master's probe tick when its authority content digest has changed or a member is behind, so a member may lag by up to one probe interval; nothing waits on a replica.

POST /api/v1/pool/transfer

Perform one step of a pool master change or eject on this host

Pool peer to pool peer over pinned mutual TLS, bounded to 256 KiB (protocol.PoolTransferLimit) with no trailing JSON. activate, abort and leave are accepted only from this host's current pinned pool master; repoint is accepted from any current ready member, because the host issuing it has just become the master and this host does not know that yet — which is exactly what the pool-CA signature on the notice proves. Every action is idempotent by operation_id: the same request repeated after a lost reply returns the same answer and performs the step at most once. An activation is taken only against a replica this host already holds and has verified at exactly the generation the outgoing master froze and signed away; nothing here recomputes or invents authority. A re-point is adopted only from a signed notice whose membership generation is strictly higher than this host's. Automatic BMC-only promotion is reported through the same optional automatic status field; older Core versions omit it.

POST /api/v1/pool/fence-checks

Report what this host found on the other hosts' fence devices

Served by the pool master. Every ready host periodically reads every other host's management controller over the recorded fence profile and the replicated credential, asking which machine it manages and reading that machine's power state, and sends the results here. The read is non-destructive by construction: no power-off is reachable from that code path. The member certificate says which host is calling and the whole report is credited to that host; a claim it makes about its own row is dropped, because a host does not get to say whether it can be shut out. The master keeps these in memory, overlays them on the membership it reports and never writes them into its durable membership record, so a pool's signed authority does not move because a check ran; a master that restarts reports "not checked yet" until the next pass. Safe to repeat: a later report replaces the caller's previous one. Body at most 64 KiB.

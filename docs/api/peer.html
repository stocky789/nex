Nex Core pool peer API — 0.1.0

Internal Core-to-Core pool peer contract; not a client or Controller API. Nex Controller never calls it and holds none of its state: membership, the pool CA, repository reservations, pool VM execution records and clustered-storage operations are durable on the pool master Core (peer probe leases and access observations are process-local). Served on the dedicated peer HTTPS listener (--pool-peer-listen, default :9444, on nex-core-local and nex-core-agent), TLS 1.3 only, with server limits of 5 s header, 15 s read, 30 s write and 16 KiB headers. The listener requests a client certificate and verifies it against the pool CA when presented; every route except join then admits only the peer named by its security requirement. Clients pin the pool CA and expected host ID (and, master to member, the membership certificate SHA-256), refuse redirects and time out after 15 s. Errors are short text/plain bodies. Development protocol: deploy matching Core versions in a pool; additive acknowledgements (probe mode echo, update_accepted, spec_match) let newer peers fail closed against older ones.

POST /api/v1/pool/join

Redeem a pool join offer

Served by the pool master; the only peer route without a client certificate. Authority is the single-use offer created by the master Core local API: it binds pool, master host, member host ID and CSR SHA-256, and expires after 15 minutes. The master signs the CSR with the pool CA, appends the member as ready, increments the membership generation and persists before replying. A retry of the same offer, host ID and CSR after a lost response returns the same certificate and current membership; a different key or an already-admitted host is refused. The member pins the pool CA and master host ID from the offer, verifies the returned certificate against its pending key, then persists and completes a Core-owned rehome. Body at most 1 MiB.

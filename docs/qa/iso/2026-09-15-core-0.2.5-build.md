# Nex Core 0.2.5 build and publication

Date: 2026-09-15. Same developer workstation and toolchain as the
[0.2.4 build](2026-09-15-core-0.2.4-build.md): the version resolved from the changelog
(`scripts/release-version.py --current --format both` → `0.2.5 0.2.5`), `bash installer/build.sh`
with `NEX_VERSION=0.2.5`, then `packaging/controller/build.py --source dist/nex-source.tar.gz
--version 0.2.5` for the Controller package from the same source archive the ISO embeds.

0.2.5 carries BUG-0189 (a refused storage credential no longer stops the Core agent) and the
SMB/NFS reliability fixes found in native lab testing: BUG-0190 (remote mounts retried after a
boot-time failure), BUG-0191 (the exclusive disk check no longer refuses because another VM's
repository is unmounted) and BUG-0192 (an interrupted shared VM update settles from observation
and no longer blocks the rest of the pool). Built from commit `cbeac4c` ("Release 0.2.5 …"): the embedded
source archive was generated after that commit, and the tracked source still matched it after
publication.

## The fixes are in the artifacts, not just the tree

- The source archive the ISO and Core package embed contains each fix: `withoutRequestURL`
  (`internal/agent/storage_credentials.go`), `StartRemoteMounts`
  (`internal/vmhost/storage_mounts.go`), the `os.ErrNotExist` skip (`internal/vmhost/engine.go`),
  `ReconcileRemoteVMUpdate` (`internal/vmhost/managed.go`) and the `vm-media` outcome kind
  (`internal/agent/run.go`). The archive does not include `CHANGELOG.md`; the version comes from
  the changelog at build time and is checked on the packages instead.
- The Core package's `/usr/lib/nex/nex-core-local` executable contains the new
  `remote storage is not mounted` and `credential handoff failed` strings.
- Before building, `go test -race ./...`, the API reference check, the documentation gate, the
  privacy test and the release-version test passed on the same tree. The Core agent built from
  that tree was run in the disposable nested lab described in the BUG-0190–0192 ledger entries.

## Publication

Published by hand from the build workstation to the website host over SSH as the publishing
account, running the commands the release workflow runs: `sudo -n /usr/local/sbin/nex-apt-publish
<core-local.deb> <controller.deb>` for the signed APT archive, then `release-publish.py --iso <iso>`
for the download tree. Retention was `--keep 6` rather than the workflow's `--keep 3`, so no
earlier release was pruned; the tree holds `0.1.6~alpha1`, `0.1.8`, `0.2.2`, `0.2.3`, `0.2.4` and
`0.2.5`, with `latest` pointing at `0.2.5`. The staging directory was removed.

Verified afterwards over public HTTPS, the same checks the workflow makes:

- `/apt/dists/nex/InRelease` → 200.
- `/apt/dists/nex/main/binary-amd64/Packages` → 200 and lists `nex-core-local 0.2.5` and
  `nex-controller 0.2.5`; both pool files return 200 with byte sizes equal to the built packages.
- `/downloads/0.2.5/nex-core-0.2.5-amd64.iso.sha256` → 200 and equals the built ISO digest.
- `/downloads/latest/` serves `nex-core-0.2.5-amd64.iso`.
- Both packages were downloaded again from the public archive: their SHA-256 digests equal the
  built packages (`03bc7fe2…a306` for `nex-core-local`, `89493a77…2e62` for `nex-controller`).

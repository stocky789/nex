# Nex Core 0.2.3 ISO build

Date: 2026-09-15. Local developer workstation (Arch Linux host, Docker 29.6.2 without the
`buildx` component, `/dev/kvm` present), `bash installer/build.sh` with the version resolved from
the changelog (`scripts/release-version.py --current` → `0.2.3`).

**The ISO was built from the working tree, not from a commit.** It therefore contains uncommitted
work: the console media fixes for BUG-0184/BUG-0185 and the in-progress 0.2.3 installer/packaging
changes that were already in the tree. Nothing here establishes that a published 0.2.3 release
matches this image.

## Build failure and fix (BUG-0186)

The first run failed after the Controller appliance and the Core package had already been rebuilt:

    Step 3/4 : COPY --chmod=755 build-matched-dlm.sh /usr/local/bin/build-matched-dlm
    the --chmod option requires BuildKit.
    Unable to find image 'nex-dlm-pacemaker-abi:latest' locally
    matched dlm-controld build did not produce its pinned package

`COPY --chmod` is BuildKit-only syntax and this Docker install has no `buildx`, so `docker build`
used the legacy builder that every other Nex image builds on. `packaging/cluster-storage/Dockerfile`
now uses a plain `COPY` with `RUN chmod 755`, which both builders accept.
`python3 -m unittest discover -s tests -p 'test_storage_packaging.py'` passed (14 tests) and failed
on the old file with `packaging/cluster-storage/Dockerfile needs BuildKit; the legacy builder cannot
run it`.

## Publication

Published by hand from the build workstation to the website host over SSH as the publishing
account that owns the download tree, running the two commands the release workflow runs:
`sudo -n /usr/local/sbin/nex-apt-publish <core-local.deb> <controller.deb>` for the signed APT
archive, then `release-publish.py --iso <iso>` for the download tree. The Controller package was
built with `packaging/controller/build.py` from the same `dist/nex-source.tar.gz` the ISO embeds;
both packages declare `0.2.3`. Retention was `--keep 4` rather than the workflow's `--keep 3`, so
no older release was pruned; a later release run with the default will prune the oldest.

Verified afterwards over public HTTPS, the same checks the workflow makes:

- `/apt/dists/nex/InRelease` → 200, PGP-signed index.
- `/apt/dists/nex/main/binary-amd64/Packages` → 200 and lists `nex-core-local 0.2.3` and
  `nex-controller 0.2.3`; both pool files return 200 with byte sizes equal to the built packages
  (715 890 836 and 131 666 388).
- `/downloads/0.2.3/nex-core-0.2.3-amd64.iso.sha256` → 200 and equals the built ISO digest.
- `/downloads/latest/` serves `nex-core-0.2.3-amd64.iso`.

The staging directory on the host was removed afterwards.

## Not covered

- No installation was performed: the smoke run used boot-menu mode only, not
  `--kernel/--initrd` offline-install mode, so first boot, services and the installed host were not
  exercised from this image.
- No physical hardware, no Secure Boot, no upgrade from an earlier installed host.
- Hosted GitHub/Gitea release workflows were not run: no `v0.2.3` tag or forge release exists, and
  the published artifacts were built locally from the working tree whose content was committed as
  "vm: add force reboot and recover guest-ejected media" and "packaging: keep storage image
  compatible with legacy Docker". A later release run will rebuild and replace them.
- No enrolled host was updated from the published archive: `apt update` and an actual
  `nex-core-local`/`nex-controller` upgrade were not exercised, so the served index and packages are
  proven reachable, not proven installable.
- The BUG-0184/BUG-0185 console media fixes inside this image were verified only with simulated

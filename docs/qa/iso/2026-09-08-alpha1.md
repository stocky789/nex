## Result

**Run 3 passed unattended, exit 0.** Actual serial logs and menu captures were inspected.

- BIOS and UEFI branded menus rendered correctly: [BIOS](bios-menu.png), [UEFI](uefi-menu.png).
- BIOS-mode Debian Installer installed Nex Core onto a fresh disk with **no virtual NIC**.
- Installed disk booted with the ISO removed. Required virtualization/host packages were installed;
  `libvirtd`, `ssh`, and `chrony` services were active, and `/dev/kvm` existed.
- Real installed GRUB displayed **Nex Core GNU/Linux**. `/etc/os-release` reported `NAME="Nex Core"`,
  `ID=nex-core`, and `ID_LIKE=debian`; upstream `/usr/lib/os-release` and `/etc/debian_version`
  remained Debian. Checks passed before and after reinstalling `base-files` version `13.8+deb13u6`.
- Libvirt defined and started a `type=kvm` nested guest using the installed kernel and a tiny
  BusyBox initramfs. Guest userspace emitted `NEX_NESTED_KVM_BOOT_PASS`. The fixture explicitly
  stopped that disposable guest before shutting down the host.
- A second installed-host boot retained Nex identity, a written host marker, and the libvirt VM
  definition. Both host boots completed their checks and powered off without manual intervention.

Observed markers: `NEX_SMOKE_INSTALL_PASS`, `NEX_SMOKE_IDENTITY_PASS` (three occurrences),
`NEX_NESTED_KVM_BOOT_PASS`, `NEX_SMOKE_FIRST_BOOT_PASS`, and `NEX_SMOKE_REBOOT_PASS`.
No QEMU test processes remained after completion.

## Environment and reproduction

QEMU on an Intel host with KVM and nested virtualization enabled. Each installation uses a new
24 GiB sparse regular file; no host block devices, live networks, or physical machines are modified.
The temporary initrd supplies disposable credentials and disk answers; these are absent from the
shipping ISO. A test-only installed service runs checks and powers off the disposable VM.
Do not distribute the test disk as a host image.

The host's OVMF/KVM combination stalled at the EFI loader with both unmodified Debian and Nex media.
UEFI menu verification therefore uses QEMU TCG, q35 and the Debian OVMF package downloaded by the
ISO builder. This establishes a working UEFI media path, not KVM/OVMF compatibility on every host.
BIOS installation and the nested guest check use KVM.

```sh
docker run --rm -v "$PWD:/work" --entrypoint dpkg-deb nex-iso-builder \
  -x /work/.cache/nex-iso/debs/ovmf_2025.02-8+deb13u1_all.deb \
  /work/.cache/nex-iso/qa-firmware
python3 tests/integration/iso-smoke.py dist/nex-core-0.1.0-alpha1-amd64.iso \
  --output .cache/nex-iso/qa-20260908-3 \
  --kernel .cache/nex-iso/stage/install.amd/vmlinuz \
  --initrd .cache/nex-iso/stage/install.amd/initrd.gz \
  --uefi-code .cache/nex-iso/qa-firmware/usr/share/OVMF/OVMF_CODE_4M.fd \
  --uefi-accel tcg
```

Choose a fresh output directory when rerunning; the runner refuses existing directories.
Detailed commands, serial logs, intermediate captures, and raw disk are local artifacts under
`.cache/nex-iso/qa-20260908-3/`. They are not a committed/public download.

## Earlier diagnostic runs

Run 1 reproduced installer debconf descriptor failures during package setup; replacing raw `chroot`
with Debian Installer's `in-target` fixed them. Run 2 proved installation and KVM boot but required
manual QMP termination during the first shutdown because the tiny guest halted without ACPI and
libvirt waited 300 seconds. The fixture now explicitly stops that guest. Run 3 independently
repeated the installation and both boots without that intervention; only run 3 verifies the final hash.

## Coverage limits

The nested guest check proves a kernel and BusyBox userspace boot, not a fully installed guest OS,
guest networking, or persistent guest-disk writes. Persistence checks cover the host marker and VM
definition. Same-version `base-files` reinstallation is not proof of every future distro upgrade.

UEFI installation, Secure Boot enforcement, multiple-disk safety, physical Intel/AMD machines,
SSH login, controller enrollment, restore/migration and the full Phase 0/3 gates remain unverified.
The installed VM also logged a `systemd-ssh-generator` AF_VSOCK CID warning with no vsock device
present; ordinary `ssh.service` was active. Chrony service activity does not establish time synchronization.

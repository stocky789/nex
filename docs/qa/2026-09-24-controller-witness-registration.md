# Controller witness registration QA

Date: 2026-09-24. This check covers the Controller witness candidate and registration slice plus native qnetd behavior in disposable Debian 13 containers. No live Nex appliance or pool was contacted. The systemd fixture exposed the workstation's cgroup namespace, as noted below.

## Contract and state

The Controller exposes authenticated agent mTLS routes:

- `GET /api/v1/agent/witness/candidates` returns same-site pool master candidates with no CA or pin, excluding the requesting pool, and a Controller candidate with runtime CA PEM and its DER SHA-256 pin. Candidate addresses identify the pool master's qnetd port; the Controller address is empty for Core to derive from its pinned Controller URL.
- `POST /api/v1/agent/witness/register` accepts `pool_id`, deterministic `cluster_name`, reported `fencing_generation`, and one PEM `csr_pem`; it returns `address` (empty), `certificate_pem`, `ca_pem`, and DER `ca_sha256`.

Only a fresh authenticated current pool master may call either route. Registration additionally requires its reported membership to identify that pool/master and match the requested fencing generation. The CSR signature, deterministic common name, and absence of extensions are checked before native signing. Invalid input returns 400, stale or unauthorized pool authority returns 409, unavailable runtime qnetd CA/service/signing returns 503, and storage/internal failures return 500. Repeating a valid registration is safe: native signing overwrites that cluster's exported certificate and returns a new valid certificate under the current CA. No pool witness configuration is saved in Controller storage; Core owns and reports the durable pool configuration. Controller qnetd NSS and its CA exist only under `/run` and rotate after runtime loss.

## Disposable Debian 13 checks

Used Debian 13 (`trixie`), systemd 257.13, `corosync-qnetd` 3.0.3-2 and `libnss3-tools` in a privileged container booted with systemd as PID 1. The fixture used the host cgroup namespace and mounted the host cgroup tree read/write; it was not isolated from that workstation control surface. Installed the appliance qnetd drop-in and runtime initializer, redirected the package NSS path to `/run/nex-witness/nssdb`, ran `systemd-tmpfiles --create`, enabled and started `corosync-qnetd.service`, and observed `ExecStartPre` complete successfully. `systemctl status` showed the configured command with `-S nss_db_dir=/run/nex-witness/nssdb`; the native status command reported `QNetd address: *:5403` and `TLS: Required (client certificate required)`. Its control socket was mode `srwxrwx---` and owned by `coroqnetd:coroqnetd`.

Installed the appliance `nex-controller.service` unit and ran it with a disposable test runner in place of the production executable. The runner invoked the rebuilt gated `TestQnetdLiveReadiness` under the unit's actual `User=nex-controller`, `SupplementaryGroups=coroqnetd`, `ProtectSystem=strict`, `ReadWritePaths=/run/nex-witness/nssdb`, private temporary directory, and other hardening settings; it successfully exercised authenticated candidate retrieval and two registrations of the same CSR against the running native qnetd service. `systemctl show` confirmed the expected identity and filesystem properties. The generated certificate was readable by `coroqnetd`. This tests the installed unit sandbox and native route code, but not the full production Controller executable. A plain TLS ClientHello is not used: qnetd's qdevice protocol performs framing before its TLS exchange, so native `corosync-qnetd-tool -s` is the readiness source.

`certutil -L -d sql:/run/nex-witness/nssdb -n 'QNetd Cert'` reported server subject `CN=Qnetd Server`. qnetd was invoked with `-S nss_db_dir=/run/nex-witness/nssdb`, tying that native server certificate to the runtime database reported by the readiness code.

The native signer was run twice as `nex-controller` with the same DER CSR and cluster name. Both calls printed `Signing cluster certificate` and `Certificate stored`; OpenSSL verified the resulting DER certificate against the runtime CA. The first check found the native wrapper wrote DER bytes to its `.crt` output as `nex-controller:nex-controller 0640`, which qnetd could not read. The Controller now changes only that generated certificate to `nex-controller:coroqnetd 0640`, parses exactly one DER certificate, and returns it as PEM; a repeated signer check confirmed `runuser -u coroqnetd -- test -r .../cluster-....crt` succeeded and OpenSSL verification passed. The CSR supplied by Core is PEM (`certutil -R -a`); Controller decodes it and writes its DER request bytes because Debian's `corosync-qnetd-certutil -s` requires DER input.

Ran Core's exact `certutil -R -a -d sql:<test-db> -s CN=nexpool12345678 -o qdevice-net-node.crq -f <password-file> -z <noise-file>` command in disposable Debian 13. OpenSSL parsed the emitted PEM request as `subject=CN=nexpool12345678`; it had no requested extensions, matching the Controller CSR validation.

## Restart and runtime CA rotation

`systemctl restart corosync-qnetd.service` preserved the CA DER. To simulate `/run` loss, stopped qnetd, removed `/run/nex-witness/nssdb`, recreated it using the appliance tmpfiles rule, and started qnetd again. The qnetd `ExecStartPre` regenerated the CA; its DER SHA-256 changed from `38782a6a745221348ec0aaf09f9fcd402164c8c4de7d45e8f5060eb371d1f7fe` to `b6dc0e5cf1d00ca6ee828834d63c5f5aa0db2218e890212522345df9cbaa9673`. Starting the Controller unit again reran the live authenticated candidate and registration test; two registrations of the same CSR passed under the new CA. OpenSSL verified the resulting native DER certificate against the rotated CA, and `coroqnetd` could read the generated certificate.

## Automated checks and limits

`go test ./internal/controller -run '^(TestWitnessEndpointsAuthenticateMasterAndCheckGeneration|TestSameSiteWitnessCandidatesExcludeRequestingPool)$' -count=1` passed. `go test ./internal/controller -count=1` passed. These tests cover unauthenticated access, stale fencing generation, wrong CSR common name, and self-pool exclusion; they do not exercise a complete Core-to-Controller network call.

The Controller unit's sandbox was exercised with a disposable test runner in place of the production daemon, not with the production Controller process. No real qdevice TLS exchange or Corosync cluster was started. `/run` loss was simulated by deleting the runtime directory in the container; no physical reboot or real appliance was tested. A workstation desktop compositor crashed shortly after this host-cgroup-enabled container started; the journal records a compositor library segfault, but does not establish causation. The container was removed and this fixture method is suspended. The separate [runtime CA QA](2026-09-24-qnetd-runtime-ca.md) records the package lifecycle check.

## Campaign and observations

The standalone probe is [`tests/integration/recovery_s0_interrupt.py`](../../tests/integration/recovery_s0_interrupt.py). It reuses the existing native S0 helpers and is restricted to the assigned disposable Core candidate. It creates a two-disk BIOS domain, writes distinct markers and nonoverlapping payload extents at three recovery points and the current point, and validates every marker, payload, and backing chain before deleting the oldest point. Point B carries an 80 MiB extent on each disk to keep the tested commit visible under the candidate's resource cap; all ranges fit inside the existing 128 MiB test disks. The campaign waits for an actual target-specific `Block Commit` job, checks that the job and deletion client remain active immediately before killing the selected libvirt daemon, then starts that same service and checks the new process identity.

Three earlier runs stopped before killing libvirtd. The first parser recognized a different job label and classified native `Block Commit: [ 0.00 %]` as unknown. The next parser recognized that label but checked stdout only, while libvirt emitted the progress line on stderr; it also classified the query as unknown. Both clients were reaped, and read-only reconciliation showed deletion had completed coherently. The third run observed the job but found it had ended before the final pre-kill check, so it stopped without killing the daemon. Those three domains and their images remain preserved.

The fourth run observed vda's `Block Commit` at 30.46%, then killed the selected libvirtd process with SIGKILL. Systemd restarted libvirtd with a new process identity. The original virsh client reported a disconnect and failed snapshot deletion. Immediate read-only reconciliation found the domain paused, all three snapshot labels still present with point C current, and no active `snapshotDeleteInProgress` flags. vda remained a commit job at 99.99%; vdb had no current job. Additional read-only captures saved live/inactive domain XML, snapshot XML, job output, file metadata, QMP state, and the daemon journal. No snapshot-delete retry, job finalize, guest resume, cleanup, or outer-host shutdown was attempted.

## Restart-recovery regression status

The tracked interruption probe now captures the native persisted domain status at the active block-job boundary, before the final active-job recheck and daemon signal. It records whether the `<snapshotDelete/>` job marker is present. After restart, it requires terminal disk jobs from virsh, QMP, and persisted status before it can stop the paused synthetic guest. It then checks the exact A/B/C graph and flags, verifies B/C/current while allowing point A's contents to differ, and makes at most one reconciled point-A delete attempt before QEMU reopen and final shutoff checks. Both point-A marker and payload reads must complete the requested byte counts before retry; a content mismatch is recorded, while an incomplete or failed read blocks retry. Any ambiguous state preserves the fixture and returns without another delete.

The six-patch `+nex2` package set is installed and the probe ran on that exact candidate. Its native result is unresolved as described above; it does not validate successful restart recovery or safe retry behavior. The earlier successful cancellation/retry evidence is from the separate four-patch `+nex1` candidate and is not evidence for the six-patch marker behavior. S0 remains open.

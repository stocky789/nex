# Recovery S0: native full backup feasibility

Date: 2026-09-25. Status: **native online full backup, owner-only outputs, local-copy restore, stopped conversion restore, and preserved source-chain reopen passed on a locally patched libvirt build in a disposable synthetic guest. Cancellation, shutdown interruption, and real capacity exhaustion were exercised. A snapshot leaf was deleted with checkpoint metadata present; its parent snapshot and checkpoint remained. S0 remains open.**

## Candidate and scope

The selected Core candidate was Debian 13 (trixie) with `nex-core-local 0.3.6~recovery.s0`, libvirt `11.3.0-3+deb13u3+nex1` (virsh reports 11.3.0), and QEMU/qemu-utils `1:10.0.13+ds-0+deb13u1` (QEMU reports 10.0.13). The candidate first received only the 15 installed libvirt runtime packages from build `final-66f0b77ea71c`, each version `11.3.0-3+deb13u3+nex1`; all artifact hashes matched that build manifest. After source-chain diagnostics, it received the exact same 15-package closure from build `final-partial-chain`, including the nested backing-chain profile correction. Its complete 89-entry manifest verified; manifest SHA256 is `cff3efad36d95a0f0a48482b03b3889e989420c9d8933d2938358c21dedb1983`, recipe SHA256 is `b85096d6561ff8538c9dd5220e88ccc44010ddf802ae1d3f428fa2e5aeef6106`, and `.dsc` SHA256 is `d796e7147c910be30c0ac9990af14ee6c717c4acd18a39860f925ac1ee5b2e9f`. Both installs simulated as 15 reinstalls, zero new packages and zero removals. The final patched package set restarted `libvirtd`; the synthetic guest was built from the verified Debian 13 generic-cloud image and had two virtio qcow2 disks, cloud-init, QEMU guest agent, and a loopback-only VNC display. It was not an application workload or an ISO-installed Core host.

## Observations

| Check | Result |
|---|---|
| Online native full backup | `virsh backup-begin --reuse-external` with explicit targets for both writable disks completed. `domjobinfo --completed --rawstats` reported job type 3, success 1, 18,253,611,008 bytes processed and zero remaining. The guest stayed running and wrote a distinct post-backup marker to each disk. |
| Independent full outputs | `qemu-img info --backing-chain` run as `libvirt-qemu` found one standalone qcow2 file for each disk, with no backing file. |
| Repository confidentiality | The canonical owner-only run created reusable targets as `libvirt-qemu`, mode 0600; no world-readable permission workaround was used. |
| Existing external snapshot | An external disk snapshot existed during the successful online full backup and remained available for stopped inspection afterward. |
| Checkpoint and snapshot interaction | On the preserved source chain, a native full backup to local disposable files completed while its external snapshot and existing checkpoint were present; both metadata entries remained after source restart. On a separate disposable overlay branch, creating an external snapshot and then completing a checkpointed full backup both succeeded. The branch heads were copied byte-for-byte, with their qcow2 backing references still resolving to the preserved source base files; the source was shut off during branch tests. A second external snapshot while the checkpoint existed and reverting the first snapshot after graceful shutdown also succeeded; checkpoint metadata remained listed. Under the six-patch build, native `snapshot-delete` of that branch's leaf snapshot succeeded while the checkpoint remained listed; the parent snapshot remained. This checks leaf deletion only, not parent deletion, chain consolidation, or general incremental/CBT compatibility. |
| Incomplete/corrupt detection | On an exploratory output, qemu-user copies truncated to 512 bytes and with a damaged header were rejected by `qemu-img check`. This is not a manifest-level or application-level integrity test. |
| Exploratory independent guest restore | An exploratory run using mode 0644 outputs booted a fresh VM from writable overlays backed by those exports while the original disk tree was unavailable; both disks showed the backup-point markers. ## Reproduction and evidence

Run only on an explicitly assigned disposable Core candidate and a fresh ignored evidence directory, with a unique writable child of the assigned NFS mount:

```sh
python3 tests/integration/recovery_s0_backup.py \
  --lab-dir .cache/recovery-s0-core.<selected-run> \
  --evidence .cache/recovery-s0-backup-evidence.<unique-run> \
  --destination /mnt/recovery-s0-nfs/<assigned-child> \
  --enospc-root /mnt/recovery-s0-capacity-final/<assigned-child>
```

The optional `--enospc-root` selects one empty child on a separate, dedicated small file-backed NFS mount. The `--enospc-only` mode skips the normal backup destination and exercises only the bounded ENOSPC case on a fresh disposable guest. A completed native job with `success=0` remains a failure even when output files exist or pass structural checks. The mode verifies the source state and detached job, checks writes on both source disks, and compares failed-output hashes around those writes. It never removes failure outputs. This mode is native-lab evidence and is not run by ordinary unit-test CI.

The earlier canonical run exited successfully after recording versions, resolved backup XML, completed job statistics, target owner/mode, standalone image inspection, hashes, and snapshot/checkpoint observations. Its successful cleanup explicitly removed both snapshot and checkpoint metadata. Failure-case artifacts are intentionally retained. The six-patch preserved-source retry and checkpointed leaf-delete walkthrough have raw command output in ignored `.cache`; they are not part of the tracked canonical harness. The ENOSPC-only tracked attempts after the harness change ended failed at the documented source-state/finalizer errors; the later identity-bound continuation passed its marker and output-hash checks, but it is not a successful harness run. `python3 -m unittest tests/test_recovery_s0_backup.py` passes 9 focused tests. The synthetic guest writes markers only; no application consistency or real workload recovery was tested.

## Limits and remaining gate

Direct restore from mode-0600 NFS paths under the libvirt VM profile, parent/non-leaf snapshot deletion with a checkpoint, incremental/CBT compatibility, multi-host behavior, physical storage failure domains, and application-consistent recovery remain open. The corrected tracked ENOSPC-only native path passed only for the tested disposable guest and filesystem profile. Cancellation, shutdown interruption, and genuine ENOSPC produced terminal failures in this synthetic guest; partial files remain unpublishable regardless of whether they are structurally readable. The mode-0644 exploratory run is not the owner-only result. These locally patched libvirt builds have only been tested in this disposable lab and are not production support claims. No S0 completion follows from these runs.
